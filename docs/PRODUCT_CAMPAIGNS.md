# Товарные кампании ArtFarfor

## Границы

Товарная кампания здесь — отдельная ЕПК с объявлениями ShoppingAd по штатному
YML-фиду InSales. Это не конвертация старых объявлений на месте.
Только PAY_FOR_CONVERSION, цель Ecommerce-покупки 352606262, счётчик 99041859.
Корзины, клики, лиды, пакетные стратегии и автоматическая смена цели запрещены.
Это новое ограничение создания/редактирования, а не утверждение о настройках
всех уже существующих кампаний. Достижение покупки не доказывает оплату заказа.

Ни один инструмент модели не одобряет и не применяет карточку. Реальный клик
владельца в Telegram обрабатывает native-команда /yd. Не вызывать /decision
через shell, не подставлять sender_id, не обходить карточки старым API.

## Фид

В InSales: Товары -> Товарные выгрузки -> Упрощённое описание. Выбрать категории,
выгрузку остатков и правильные склады, включить исключение отсутствующих товаров.
Нужна постоянная HTTPS-ссылка на artfarfor.com. Скачанный XML — снимок для проверки,
не автообновляемый источник. Не угадывать URL по имени файла.

`product_catalog({feed_url})` проверяет XML, дату, IDs, категории, цены, наличие,
URL и фото. Стандартная декларация shops.dtd разрешена без загрузки DTD;
сущности и произвольные DTD запрещены. Категории и наличие не генерируются моделью.
Для создания допускается только выгрузка без некорректных/недоступных товаров.
`product_feeds({})` читает фиды Директа и их состояние.

Директ обновляет URL-фид самостоятельно, не мгновенно. Бот не редактирует остатки
в InSales и не считает отсутствие товара доказательством продажи. Проданные товары
должны исключаться штатной выгрузкой по фактическим остаткам. До первого запуска
владелец проверяет правильность складов и исключение отсутствующих позиций.
Нельзя обещать мгновенное прекращение показов после продажи.

## Черновик

`product_draft({draft: {...}})` сохраняет локальный черновик, ничего не создаёт в Директе.
Пример структуры, а не утверждённые настройки:

```json
{
  "name": "Товары | Категория | ArtFarfor",
  "feed_url": "<проверенный URL от владельца>",
  "placement_type": "search_only",
  "region_ids": [225],
  "target_cpa_rub": "1000",
  "weekly_budget_rub": "20000",
  "replacement_for_campaign_id": 123,
  "groups": [{
    "name": "Категория",
    "category_ids": ["<ID из проверенного фида>"],
    "default_text": "Подходящий товару текст до 81 символа",
    "offer_ids": []
  }]
}
```

Бюджет, CPA и регионы не наследовать молча. Если их нет — один вопрос за раз.
placement_type: search_only, network_only, both; выбирать явно.
replacement_for_campaign_id необязателен и только связывает пилот с прежней кампанией.
groups: 1..10, выборки не пересекаются. category_ids обязательны. Пустой offer_ids
означает все доступные товары выбранных категорий и текущих подкатегорий. Непустой
список ограничивает выборку максимум 50 числовыми ID. Новые товары внутри выбранных
категорий попадут в рекламу при обновлении URL-фида; сообщить это владельцу.
В товарном объявлении API принимает один DefaultText. Это не схема 7/3 ResponsiveAd.
Текущий пилот использует целевые/узкие категории автотаргетинга без конкурентов;
офферный ретаргетинг выключен до проверки соответствия ecommerce ID.

`product_get_draft({id})` читает версию.
`product_draft_revise({id, revision, draft})` заменяет только этот черновик.
Старые карточки создания после правки недействительны.

## Независимые карточки

Все действия готовятся через `marketer_propose({proposal:{action:{...},reason:"..."}})`.
reason необязателен для оперативных действий; при замене приводить реальные факты.
Не отправлять несколько действий в одной карточке.

| kind | Остальные обязательные поля action | Результат одобрения |
| --- | --- | --- |
| product_feed_register | feed_url | Регистрация URL-фида, без кампании. Дождаться DONE и ненулевого NumberOfItems. |
| product_create | draft_id, draft_revision | Создание остановленной кампании, групп, товарных объявлений и автотаргетинга. Без модерации/показов. |
| product_edit | campaign_id, patch | Одно поле: name, target_cpa_rub либо weekly_budget_rub. |
| product_ad_edit | campaign_id, ad_id, patch | Одно поле: default_text, category_ids либо offer_ids. |
| product_moderate | campaign_id | Отправка всех черновых объявлений этой кампании на модерацию. Кампания остановлена. |
| product_launch | campaign_id | Запуск принятой модерацией кампании после свежей проверки покупки и фида. |
| product_pause_old | campaign_id, replacement_campaign_id | Остановка только старой кампании. Замена должна быть связана, активна и платить за покупку. |

`marketer_revise` меняет только указанную карточку и требует нового одобрения.
`product_inspect({campaign_id})` читает настройки/объявления/состояние создания.
Редактирование и запуск поддержаны для полностью созданных ботом товарных кампаний.
Произвольные старые товарные кампании автоматически не импортируются.
Изменения извне блокируют запись до сверки, чужие настройки не затираются.

Каждый запрос на запись заранее заносится в журнал. После неизвестного/частичного
результата повтор запрещён: `product_operation({id:<ID карточки>})` показывает шаги
и полученные IDs. Сверить Директ и журнал до дальнейшей работы; не удалять блокировки
и не обходить их новым черновиком. Автоматического удаления частичных объектов нет.

## Анализ и замена

`product_candidates({})` использует последний зрелый снимок не старше 7 дней.
Unknown не равен нулю. Кампании с подтверждёнными покупками сохраняются по умолчанию.
Предварительный кандидат: полный числовой ноль покупки при >=100 зрелых кликах
и подтверждённых счётчике/цели; либо >=10 покупок и CPA выше 1.5 текущего целевого.
Это порог для человеческой проверки гипотезы, не доказательство убыточности.
Учесть период, атрибуцию, оплаченность, маржу, лаг и обучение.

Существующий еженедельный аналитик получает эти данные без нового расписания.
Он может предложить отдельный ручной план товарного пилота. После его одобрения
интерактивный бот разрабатывает черновик и выдаёт исполняемые карточки; одобрение
ручного плана само кампанию не создаёт. Создание, запуск и выключение прежней
кампании всегда разные решения. Эффективные кампании не заменять массово.

## Проверка и ограничения

Sandbox принял тестовый фид, но campaigns.add ЕПК вернул HTTP 500 NotImplemented.
Поэтому полный create/update ShoppingAd не подтверждён реальным sandbox прогоном.
Контракт и защитные сценарии покрываются mock-тестами; это не заменяет проверку
первого остановленного боевого пилота после отдельного одобрения владельца.
Не заявлять «всё проверено в Яндексе» до успешного readback реальных объектов.
