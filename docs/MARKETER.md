# Полуавтоматический маркетолог

## Границы первой рабочей версии

Реализован независимый цикл: данные Директа и Метрики -> проверка достаточности -> порции анализа и общий отбор -> отдельные Telegram-карточки -> решение владельца -> точечное применение -> проверка API -> последующее наблюдение.

Аналитик рассматривает экономику, Поиск, РСЯ, креативы, посадочные, ассортимент и эксперименты. Он не обязан выдумывать предложение для каждого направления. Нет CRM, маржи, возвратов и подтверждённых оплаченных заказов: прибыль/ROI не рассчитываются. Поддержка всего маркетинга как гарантированно автономной замены человеку не заявляется.

Автоматически после подтверждения поддерживаются:
- одна полная наблюдаемая минус-фраза в одной группе;
- изменение текстовых полей одного существующего TextAd;
- одно значение CPA или недельного бюджета одноголевой PAY_FOR_CONVERSION по основной цели, не более 20%, при достаточных подтверждённых конверсиях. Статистика покупки не используется для обоснования изменения стратегии, оплачивающей другую цель.

Другие решения (новые кампании, пакетные/многоцелевые стратегии, ретаргетинг, исключения площадок РСЯ, изображения, товарный ассортимент, посадочные, CRM) оформляются как отдельные **ручные планы**. Их одобрение не выдаётся за выполнение API. Прежние интерактивные возможности бота сохранены; владелец может отдельно поручить выполнить согласованный план. В новых карточках нет автоматического создания/остановки/перезапуска кампаний.

## Расписание и данные

- `yandex-direct-marketer.timer`: понедельник, 12:00 Europe/Podgorica. Не используется OpenClaw heartbeat или частый LLM cron.
- Календарный запуск независим от ручных запусков. Первый анализ 19 сентября не отменяет понедельник 21 сентября. Таймер передаёт `scheduled: true`; SQLite атомарно резервирует понедельничный слот, поэтому повторный вызов в той же неделе не запускает модель снова. После ошибки нет слепого повтора: нужен явный ручной запуск.
- Для обычных ручных запросов без `force` сохранён минимальный интервал семь дней. Ручные проверки не занимают календарный слот. `required_review_slots: ["2026-09-21"]` задаёт одобренное владельцем повторное рассмотрение даже без прироста статистики, но не запускает модель на пустом/недостаточном срезе. Для следующих недель проверка достаточности новых данных сохраняется.
- Окна: последние 28 зрелых дней и предыдущие 28. Последние семь полных дней и сегодня исключены. Эти параметры меняются в `backend/marketer/policy.json`.
- До вызова модели: >=30 кликов или >=2 числовых конверсий одной из наблюдаемых целей; повторный анализ требует >=20 новых кликов, новых/уточнённых конверсий или расширения состава аналитики. Цели не суммируются в продажи. Сбор API без модели расходует API-квоту, а не токены модели.
- Все активные/приостановленные Unified Campaigns, если список campaign_ids пуст. Отчёты привязаны к покупке 352606262, счётчик 99041859; дополнительно собираются фактические цели стратегии.
- Директ: атрибуция кампании. Метрика: lastsign. Числа разных систем не суммируются.
- Нельзя считать прочерк `--` нулём или доказательством неисправности цели. Сохраняются исходные значения. Итоги текущего/предыдущего периода запрашиваются отдельно без группировки по дням; числовой итог не становится неизвестным из-за прочерков в отдельных днях. CPA не рассчитывается по неполному итогу. GoalTotals хранит отдельные значения целевых визитов каждой цели, полноту и CPA; общий CPA по сумме разных целей не вычисляется.
- Метрика: отдельно собираются `reaches` (достижения) и `visits` (целевые визиты) каждой фактической цели стратегии и основной цели. Есть итоги текущего/предыдущего периода по кампании и по всему счётчику, отчёты по запросам/посадочным. Запросы с большим числом целей разбиваются на пакеты до 19 метрик; изменения/дубликаты строк при пагинации отклоняются.
- При подтверждённой ошибке Метрики «Запрос слишком сложный» объединённый запрос повторяется по одной цели. Базовые визиты/пользователи не суммируются между запросами; наборы строк и базовые метрики должны совпасть. `accuracy=full` сохраняется. Другие ошибки этим механизмом не повторяются.
- Каждый цикл читает параметры счётчика и каталог целей через Management API. `diagnostics` показывает привязку счётчика, наличие/тип/статус цели и фактически наблюдаемые события, не объявляя отсутствие покупок доказанной поломкой. `CS_ERR_UNKNOWN` не считается доказательством неработающего трекера. API не заменяет реальный тест заказа и сверку оплаты.
- Остальные зарегистрированные цели (оформление заказа, звонки, формы) собираются в общем срезе счётчика, отдельно от атрибуции кампаний. Разные события покупки не объединяются в заказы. При ошибке 1000 «Сервис временно недоступен» чтение сущности Direct повторяется до трёх попыток; записи в рекламу этот механизм не повторяет.
- Даты отчётов вычисляются по `report_timezone=Europe/Moscow`, календарный таймер работает по `schedule_timezone=Europe/Podgorica`.
- Пагинация entities и Метрики обрабатывается полностью, sampled/rounded Метрика отклоняется. Отчёты Direct 201/202 ожидаются с retryIn в пределах ограниченного числа попыток.
- Полный снимок хранится в SQLite. Модели передаётся ограниченная выборка лидирующих по конверсиям/расходу/кликам строк и число всех строк. Это явно помеченная выборка, не полный просмотр всех запросов/объявлений.
- Контекст одной порции ограничен `model_context_max_bytes` (70 000 байт), весь запрос вместе с инструкциями проверяется против `model_request_max_bytes` (100 000 байт). Это защитные лимиты backend, не размер окна модели. Кампании распределяются по порциям без пропуска; исходные отчёты остаются в SQLite. После анализа порций выполняется общий отбор из готовых кандидатов: модель выбирает ID и не переписывает действия. Промежуточные результаты сохраняются. По группам передаётся до 60 записей с приоритетом групп выбранных запросов/объявлений и полное количество; по минус-фразам количество и первые пять. Это явно обозначенная выборка, не полный просмотр всех строк.
- Выборка включает вспомогательные конверсии и запросы с большим числом кликов при нулевом расходе. Аналитик обязан вернуть `coverage` всех восьми направлений: конкретное предложение, отсутствие обоснованного действия или точный пробел в данных. Неопределённость покупок не блокирует независимый анализ текстов, релевантности и структуры каналов. Актуальный штатный YML входит в цикл; HTML страниц не проверяется. Наличие и цены подтверждаются только свежим корректным фидом.

## Карточки

Каждая карточка содержит кампанию, точное действие, обоснование, числовой контекст и период, гипотезу, метрику оценки и риски. Кнопки: одобрить, отклонить, изменить, отложить, подробнее.

Краткое обоснование сокращается только с явным многоточием. «Подробнее» сохраняет полный текст, включая критерий успеха и ограничения; длинные подробности разбиваются на страницы с кнопками «Назад»/«Далее», без вызова модели. Точное действие и предупреждения в основной карточке не обрезаются. Непомещающиеся предложения отклоняются до сохранения. Для ручного плана показывается критерий выполнения, а не обещание оценки через 28 дней. Неполные конверсии с числовой суммой ноль отображаются как неизвестный итог, не как ноль достижений.

- `marketer_revise` меняет только указанную карточку и увеличивает revision. Старые кнопки одобрения перестают действовать.
- `/yd` обрабатывается нативным плагином OpenClaw без вызова модели. Проверяются канал, allowlist, Telegram sender_id владельца и отдельный ключ решения. Инструмента одобрения у модели нет.
- Повторный клик не повторяет запись. Изменения параметров извне требуют новой карточки. Добавочные минус-фразы других карточек не затираются.
- Отложенная карточка не блокирует другие и не рассылается заново навязчиво. Через семь дней исходное подтверждение истекает; для дальнейшего применения нужна новая версия с актуальными данными.
- Отклонённые/применённые действия дедуплицируются по кампании и точному действию в течение 90 дней. Необработанные, отложенные, принятые ручные и неопределённые действия не дублируются и после этого срока: используется существующая карточка/новая версия. Это защита точных действий, не гарантия семантического распознавания всех перефразировок.
- Неоднозначный ответ после записи переводит карточку в `uncertain`. Автоматического повтора нет: сначала нужна ручная сверка.
- `advisory`: одобрение -> `accepted_manual`; только отдельная отметка владельца -> `completed_manual`.
- После применения точечных изменений наблюдение начинается через срок карточки плюс лаг конверсий. Сравниваются равные по длине периоды до и после применения; сам день изменения исключается. Малая/неполная выборка откладывает вывод до 90 зрелых дней. Сравнение на уровне кампании наблюдательное, не A/B-доказательство причинного эффекта. Автоматический откат не выполняется.

## Память и эксперименты (2026-11-03)

InSales API исключён по решению владельца. Заказы, оплаты, возвраты и прибыль не появляются из YML или достижения цели. Курсы в этот этап не входят.

- Источник памяти — журнал карточек и событий SQLite. Сохраняются версии, гипотеза, критерий, состояние решения, подтверждённое применение и наблюдение. Ручное выполнение отмечается только реальным владельцем и не означает доказанный результат.
- Модель получает до трёх записей на кампанию, включая последнее незавершённое действие и последнее наблюдение с основными числами до/после, а также до восьми общих задач измерения, чтобы не размножать одну проверку по разным кампаниям. Выборка явно обозначена; интерактивный бот читает полную историю постранично. Это не переобучение модели и не хранение всей переписки в контексте.
- `marketer_memory {campaign_id:0,page:1}` читает все кампании; положительный ID ограничивает выборку. По 10 записей, `next_page` указывает продолжение. `marketer_experiment {id}` возвращает наблюдение и последние 30 событий конкретной карточки, включая прежние версии гипотез.
- `experiment_observations` хранит последнюю оценку; история остаётся в `events`. Директ перечитывается отдельными итоговыми отчётами за два периода, по исходной цели и атрибуции. Прочерки/пустой отчёт не считаются нулём, цели не суммируются в продажи.
- Операционные минимумы: 100 кликов и 10 числовых целевых визитов покупки в каждом периоде. Это не критерий статистической значимости. Статусы: `insufficient_data`, `inconclusive` после 90 зрелых дней, `data_unavailable`, `not_comparable`, `confounded`, `observed`. Последний означает наблюдение, не успех и не причинный эффект.
- Проверяются другие зафиксированные изменения той же кампании, исходная/текущая конфигурация, сохранность изменённого текста/минус-фразы. Если старый журнал не содержит исходной конфигурации, это явно отмечается. Неизвестные внешние изменения и сезонность исключить нельзя.
- Товарный запуск оценивается как отдельный `pilot_observation` по периоду после запуска, без ложного сравнения с отсутствовавшей раньше кампанией. Регистрация фида, создание/редактирование структуры и модерация — операционные действия, а не доказанные эксперименты с продажами.
- Оценка выполняется существующим недельным циклом без модели. Незавершённая оценка перечитывается не чаще раза в семь дней. Уведомление — отдельное сообщение об одном эксперименте при смене состояния; одинаковое «данных мало» не рассылается заново. Неопределённая доставка не повторяется автоматически. Возобновления/откаты/изменения рекламы не выполняются оценщиком.

## История ассортимента

- `catalog_snapshots` сохраняет наблюдаемые состав, цены, категории и явное наличие штатного YML. Неизменный каталог обновляет время наблюдения, не создавая новую копию состава.
- `marketer_assortment {}` читает сохранённое наблюдение без нового сетевого запроса. Недельный цикл обновляет фид по существующей проверенной ссылке. Актуальность ограничена 48 часами и по времени получения, и по времени генерации.
- Сравнение с наблюдавшимся состоянием на момент прошлого завершённого анализа показывает добавленные/исчезнувшие ID, изменение цены, наличия и категории. Если корректной базы сравнения нет, возвращается `no_complete_baseline`, а не выдуманные продажи. Некорректные выгрузки не используются для вывода об исчезновении товара.
- Для известных боту товарных кампаний реальные фильтры ShoppingAd сопоставляются с тем же фидом: количество доступных товаров, диапазон цен, категории и примеры. Неподдерживаемый фильтр или неполный каталог даёт неизвестный/частичный результат, не достоверный ноль.
- Изменение состава фида может открыть существующий недельный анализ при достаточном общем объёме рекламных данных, даже если новых кликов мало. Дополнительного таймера нет. Исчезновение/остаток не подтверждают продажу, HTML посадочных не проверяется, фид и реклама автоматически не редактируются.

Проверка внедрения: пробный запуск `76403c3ce875409c` обработал 12 кампаний без ошибок сбора, две порции и общий отбор. Новые предложения не отобраны: ожидающие ручные задачи измерения не продублированы. В фиде подтверждены 581 доступная позиция и четыре выборки ShoppingAd в трёх кампаниях. Карточки и реклама не изменялись. Копия перед внедрением: `/home/appuser/backups/marketer-memory-20261103-57t81hj8`.

## Инструменты интерактивного бота

`marketer_status` -> последние запуски и карточки.
`marketer_context` -> компактный снимок и история.
Если ответ содержит `overview_only`, `marketer_context_batch {batch: N}` читает каждую указанную порцию. Обзор одной порции нельзя выдавать за полный анализ аккаунта.
`marketer_proposal {id}` -> полная карточка.
`marketer_propose {proposal}` -> новая карточка без применения.
`marketer_revise {id, revision, proposal}` -> новая версия указанной карточки.

Структура proposal: campaign_id, area, title, reason, expected_effect, success_metric, evaluate_after_days (14..90), action. Допустимые area: economics, search, rsya, creative, landing, assortment, experiment, measurement.

Примеры action:
```json
{"kind":"add_negative","ad_group_id":123,"phrase":"полный нерелевантный запрос"}
{"kind":"ad_text","ad_id":456,"fields":{"Title":"Новый заголовок"}}
{"kind":"strategy_value","side":"Search","field":"Cpa","value_micros":1100000000}
{"kind":"advisory","task":"Один конкретный ручной эксперимент"}
```

Для минусации необходимы >=20 зрелых кликов, числовой ноль по покупке и всем собранным целям стратегии. Перед записью отчёт перечитывается для защиты от поздних конверсий. Утверждение «слово нерелевантно» не выводится автоматически из словаря.

## Эксплуатация

Рабочая папка VPS: `/home/appuser/.openclaw/workspace/yandex-direct-bot`.
Службы пользователя: `yandex-direct-backend` (127.0.0.1:8091), `yandex-direct-marketer` (127.0.0.1:8092), единственный `openclaw-gateway`. Второй Telegram poller не запускается.

После переноса файлов из Windows проверять права на VPS: исходники плагина должны иметь `0644`, без записи для всех пользователей. Архив может перенести `0666`; OpenClaw блокирует такой плагин. После перезапуска проверять в журнале регистрацию `proposal tools and owner /yd decisions registered`, а не только состояние `active` службы.

Приватные ключи: `~/.config/yandex-direct-bot/marketer.json` и `backend.env`, права 600. Токен Telegram берётся только из существующей конфигурации OpenClaw. Секреты, SQLite, экспорты и логи не входят в Git.

Аналитик direct-marketer имеет `tools.deny=["*"]`, отдельный контекст каждого анализа и не может выполнять команды/отправлять Telegram/менять кампании. Интерактивный direct сохраняет прежние инструменты; это не OS-изоляция от процесса того же Unix-пользователя.

Статус `/status` отдельно возвращает `analyst_auth` и обзор `coverage` последнего анализа. Ошибка обновления ChatGPT OAuth означает необходимость повторного входа, а не отказ Яндекс API. При `reauthentication_required` сбор статистики возможен, но формирование новых предложений моделью не подтверждено. Не подменять этот статус общим `active` systemd и не объявлять полный запуск успешным до реального ответа аналитика.

### Восстановление анализа (2026-11-03)

- `/status.analysis_health` разделяет последнюю успешную завершённую обработку и последнюю попытку, показывает этап, ошибку и состояния запросов модели. `running` показывает занятость единственного обработчика.
- `runs.data` сохраняет снимок, этапы и результат при ошибке; ошибка больше не затирает собранные данные. `analysis_steps` хранит стабильные ID запросов, хеш входа и результаты порций/общего отбора. Замороженный план сохраняется отдельно в SQLite.
- Сначала сохраняется запрос, затем OpenClaw получает `agent` с `deliver=false`. После подтверждения используются только `agent.wait` и `chat.history` той же изолированной сессии. При потере ответа нельзя отправлять новый запрос модели автоматически: восстанавливается результат старого. Ограниченные повторения относятся только к чтению состояния, не к вызовам модели или записи в Директ.
- Отдельно распознаётся подтверждённый отказ **до отправки RPC**: штатный клиент OpenClaw 2026.3.13 пишет `gateway connect failed: Error: gateway closed (...)` либо `gateway not connected` из обработчика ошибки `connect`, тогда как задание отправляется только из `onHelloOk`. До трёх попыток подключения с тем же ID допустимы только в этом случае, без структурированного ответа с runId/payloads. При возобновлении старой такой ошибки дополнительно требуется пустая история той же сессии. Общий таймаут, потеря ответа или другая ошибка остаются неопределёнными и не разрешают повтор задания. Это не повтор записи в рекламу.
- Служебный `POST /run {"resume_run_id":"..."}` продолжает незавершённый запуск возрастом до семи дней. Повторно не собирает уже сохранённый снимок и не вызывает модель для завершённых порций. После семи дней нужна свежая статистика. Возобновление не занимает дополнительный календарный слот и не создаёт таймер.
- `POST /run {"force":true,"publish":false}` выполняет проверку без Telegram-уведомлений, создания карточек и изменения рекламы. Статус `preview_ready` означает готовый анализ, но не публикацию. Его можно продолжить тем же `resume_run_id`; перед публикацией предложения снова валидируются.
- Неопределённая доставка карточки не повторяется автоматически. Подтверждённо доставленные карточки повторно не отправляются. Все действия в рекламе по-прежнему требуют фактического решения владельца.
- Ошибки отчётов Direct содержат HTTP/API-код, тип отчёта, кампанию, даты, поля и цели; секреты удаляются. HTTP 400 не повторяется вслепую. Ограниченные повторы чтения допустимы для 429/500/502/503/504. Недоступная кампания не превращается в нулевую статистику.
- Сбой оценки старого изменения сохраняется отдельно и не блокирует новый анализ. Модель, расписание и правила одобрения не изменены. Курсы/GetCourse в это обновление не входят.
