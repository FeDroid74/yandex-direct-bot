# Резервные копии VPS: Restic + Backblaze B2

Настройка от 13 ноября 2026. Пользователь выбрал B2 вместо R2 и запретил
подключать карту или платную подписку с оплатой перерасхода.

## Хранилище и доступ

- VPS: `vmi3751006`, production на новом сервере.
- Закрытый выделенный бакет: `vps-restic-20261113-fd74`.
- Регион и S3 endpoint: `eu-central-003`,
  `https://s3.eu-central-003.backblazeb2.com`.
- Репозиторий: `s3:https://s3.eu-central-003.backblazeb2.com/vps-restic-20261113-fd74/restic`.
- Restic **0.19.1**, repository format 2; релиз проверен SHA-256 из официального
  `SHA256SUMS`. Receipt: `/usr/local/share/vps-backup/restic-release.json`.
- Отдельный стандартный application key ограничен этим бакетом. Master key
  не генерировался и не использовался. UI Read and Write включает права
  управления выделенным бакетом; это не ключ администратора всего аккаунта.
- Конфигурация `/etc/vps-backup/config.json`, ключи `credentials.env` и пароль
  `repository-password`: root, `0600`, родительский каталог `0700`.

Репозиторий шифрует Restic до передачи в B2. Пароль не выводится в отчёты и
не включается в копию `/etc`; отдельный комплект восстановления хранится на ПК
в приватном, исключённом из Git каталоге `runtime/backup-private-20261113/recovery`.
Пароль нельзя оставлять только на исходном VPS.

## Бесплатные ограничения

В интерфейсе конкретного аккаунта подтверждены:

| Ограничение | Значение |
| --- | --- |
| Хранение | 10 GB, денежный cap $0.00 |
| Скачивание | 1 GB в сутки, денежный cap $0.00 |
| Class B | 2 500 запросов в сутки |
| Class C | 2 500 запросов в сутки |

Эти ограничения не повышались. Оповещения аккаунта о достижении cap уже были
включены. Квоты могут прервать загрузку или восстановление; такой результат
нельзя считать успешной копией. Ограничение скачивания существенно при аварийном
восстановлении: большой репозиторий может потребовать нескольких суток.

Программный storage guard — **8 000 000 000 байт** во всём выделенном бакете,
включая скрытые версии и незавершённые multipart uploads. Перед backup используется
консервативная оценка: существующий объём + весь логический staging + запас на
метаданные. Это дополнительная защита, не замена лимитам провайдера. При отказе
копирование останавливается, история не удаляется ради обхода проверки.

## Какие данные сохраняются

- `/home/appuser`: исходники, незакоммиченные файлы, `.git`, `.env`, конфигурация,
  auth/session state, outputs/provenance, Kwork JSON и браузерные профили.
- В частности, сохраняется установленный OpenClaw с локальными исправлениями,
  custom extensions и отдельный runtime AutoPublisher. Каталог внутри установленного
  модуля не исключается лишь потому, что называется `cache` или `tmp`.
- `/etc`: настройки системы, сервисы, роли пользователей и ключи SSH сервера;
  исключены пароль Restic, machine-id, resolv.conf и mtab.
- Backup helpers, их release receipt и binary Restic из `/usr/local`.
- PostgreSQL `montich_bot`: логический custom dump без внутренней компрессии;
  отдельно globals с ролями. Raw каталог PostgreSQL не копируется.

Исключаются известные загрузочные и браузерные кеши, `.venv`/`venv`, pycache,
временные рабочие каталоги, старые вложенные backups и logs. TTL research cache
AutoPublisher по умолчанию исключён; основной `auto_publisher.sqlite3` и постоянные
исследовательские outputs сохраняются. OS-пакеты и часть зависимостей при полном
восстановлении требуется установить по manifest; это не побитовый образ диска.

## Согласованность

Сначала создаётся закрытая generation в `/var/lib/vps-backup/generations`,
потом атомарно переключается стабильный `current`. Restic читает уже подготовленный
набор, а не живые базы.

- SQLite, включая базы без расширения вроде Cookies, снимаются Online Backup
  API с учётом WAL. Чтение выполняется от исходного UID, чтобы не создать
  root-owned WAL/SHM у приложения. Каждый snapshot проходит `quick_check`.
  Служба получает `CAP_SETUID` для понижения прав. Каждый SQLite worker
  очищает ambient/KEEP_CAPS, переключает UID/GID, обнуляет все capability sets
  и проверяет результат; `NoNewPrivileges` остаётся включённым.
- Scratch: `/var/lib/vps-backup-sqlite-scratch`, root `0711`, отдельные случайные
  каталоги владельца БД `0700`. Завершённые snapshots возвращаются в root-private
  staging с исходными правами владельца.
- Kwork pending копируется под существующим pending lock; остальные JSON
  проверяются как отдельные атомарные файлы. Глобальной JSON-транзакции у
  приложения нет. Lifetime lock AutoPublisher не используется как backup lock.
- AP outputs собираются повторно после снимка основной БД; SQLite внутри
  outputs также проходят native snapshot после файлового копирования.
- PostgreSQL dump проверяется через `pg_restore --list`.

Manifest явно содержит `cross_project_atomic=false`. Это согласованные отдельные
БД и набор файлов онлайн-системы, не единый атомарный снимок всего VPS или внешних
площадок. Рабочие приложения ради ежедневного backup не останавливаются.

## Расписание и хранение

Время расписаний — **Europe/Podgorica**, независимо от системного UTC сервера.

| Сервис | Расписание | Действие |
| --- | --- | --- |
| `vps-backup.timer` | Ежедневно 03:15 + до 2 минут | Staging и новый snapshot |
| `vps-backup-maintain.timer` | Суббота 04:15 + до 2 минут | Retention и bounded prune |
| `vps-backup-check.timer` | Ежедневно 05:30 + до 2 минут | Проверка целостности с ограниченным чтением |

Политика Restic: **7 дневных + 4 недельных + 3 месячных** снимка. Это объединение
календарных групп, а не обещание фиксированного числа различных snapshots.
Группировка — стабильные host/tag; timestamp generation не становится отдельной
retention group. Prune ограничен repack 256 MiB и резервом места.

**Скрытые удалённые версии B2 хранятся 7 дней**, по отдельному прямому выбору
владельца. S3 API подтвердил `NoncurrentVersionExpiration.NoncurrentDays=7`,
действующей `Expiration` нет. Это дополнительная корзина уже удалённых объектов,
не срок жизни нужных текущим снимкам файлов. Lifecycle применяется с задержкой;
скрытые объекты продолжают занимать место до фактической очистки.

Все команды разделяют один `flock`. Неполный backup или exit 3 не становится
успехом, при ошибке сохраняется прежний `last_success`. Локально остаются current
и предыдущая sealed generation; старые и неудачные попытки очищаются только из
проверенных собственных root-private каталогов.
`last_backup_attempt` отдельно хранит результат последней попытки backup:
успешная проверка репозитория не скрывает предшествующий сбой копирования.

Проверка данных использует полное чтение лишь для маленького репозитория;
для большего объёма последовательно проверяются части примерно до 400 MB.
Это приблизительный объём, не точный учёт суточного скачивания аккаунта.
В день большого restore нельзя дополнительно запускать полное чтение без
проверки остатка квоты. Проверочный таймер не догоняет пропущенные запуски.

## Управление

```sh
sudo systemctl status vps-backup.service
sudo systemctl list-timers 'vps-backup*'
sudo /usr/bin/python3 /usr/local/lib/vps-backup/vps_backup.py status
sudo systemctl start vps-backup.service
sudo journalctl -u vps-backup.service --since today
```

Статус содержит возраст последней успешной копии и признак устаревания после
36 часов. Это не отправка уведомлений о каждой ошибке в Telegram: отдельный
канал уведомлений не подключался. Ошибки фиксируются в systemd/journal и
`/var/lib/vps-backup/status.json`; B2 отправляет свои cap alerts по настройкам
аккаунта.

Суточная квота общая для аккаунта и сбрасывается в 00:00 GMT. При изменении
размера репозитория цикл проверки частей может начинаться заново; ежедневная
проверка части сама по себе не доказывает чтение всех packs за фиксированный срок.
Незавершённые multipart uploads входят в storage guard. Текущее правило 7 дней
касается noncurrent versions и не отменяет старые незавершённые загрузки;
при их накоплении требуется отдельная проверка до удаления.

## Восстановление

1. Нужны пароль Restic, конфигурация репозитория и действующий application key.
   Их копия вне VPS обязательна. Если ключ отозван, можно выдать новый доступ
   к тому же бакету; потерянный пароль Restic этим не восстанавливается.
2. Сначала восстановить в отдельную директорию. Не копировать rootfs поверх
   работающего сервера и не запускать приложения ради проверки backup.
3. Внутри снимка находятся стабильные пути
   `/var/lib/vps-backup/current/{rootfs,postgres,manifest.json}`.
   Файлы приложений — в `rootfs/home/appuser`, настройки — в `rootfs/etc`.
4. SQLite восстанавливаются из standalone snapshots без старых WAL/SHM.
   PostgreSQL — из dump; роли/globals переносятся отдельно с учётом существующих
   системных ролей. Проверить права владельцев и UID/GID.
5. До проверки внешних операций все pollers, workers и timers приложений
   должны оставаться выключенными. Восстановление БД не откатывает уже
   отправленные Telegram-сообщения, отклики Kwork и рекламные изменения.
6. Не обнулять UNKNOWN/uncertain/ATTEMPTED/submitting, claims, budgets и
   cooldown ради запуска. Даже pending из старой копии мог быть исполнен уже
   после момента backup. Требуется сверка перед включением потребителей.
7. Зависимости и часть системных binaries восстановить по manifest. Проверить
   авторизацию: cookies и OAuth refresh token могут устареть независимо от
   целостности резервной копии.

Пример восстановления PostgreSQL dump в отдельный каталог на Linux. Здесь
`/secure/recovery` — перенесённый приватный комплект, а `SNAPSHOT_ID` берётся
из `restic snapshots`. Команда не применяет dump к работающей БД:

```sh
set -a
. /secure/recovery/credentials.env
set +a
export AWS_DEFAULT_REGION=eu-central-003
restic --repo s3:https://s3.eu-central-003.backblazeb2.com/vps-restic-20261113-fd74/restic \
  --password-file /secure/recovery/repository-password \
  restore SNAPSHOT_ID --target /restore-check --verify \
  --include '/var/lib/vps-backup/current/postgres/**'
```

Для полного восстановления убрать `--include`, предварительно проверив
остаток суточной квоты. `restore --verify` проверяет восстановленные локальные
файлы; дополнительный `check --read-data` в тот же день может исчерпать лимит.
